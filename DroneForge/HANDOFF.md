## 1. The owner and the rules (these override your defaults)
- Owner dislikes extra questions, long text and wasted tokens, and is impatient. Give a crisp plan first, then do it. First line = honest status; say plainly what is unverified.
- **Metres only** (m, m/s) in replies, GCS, tools, logs. Never cm/mm.
- **THIS ARMS THE DRONE.** Before suggesting or running anything that arms or spins motors (throttle ramp, hand-lift test, GCS TAKE OFF, any script sending arm=True) the FIRST line of your message must be: "THIS ARMS THE DRONE: the motors will spin." Then say what it does, how it stops, who is on SAFE. Props stay on; FC USB must be unplugged while arming. Prefer read-only diagnostics.
- **Never flash firmware, change FC settings, arm, or delete files without the owner's explicit go-ahead.** Archive instead of deleting.
- **Battery is a warning only.** Never block arming/takeoff or auto-land on voltage.
- GCS UI rules: no QMessageBox, no QCheckBox, no "Advanced", no yes/no questions; every outcome is an inline colour-coded status line. Colours: greys + ONE soft-blue accent (`theme.ACC`), AMBER only for caution, RED only for SAFE / real alarms; state must be readable without colour. No ad-hoc hex colours: use `nimbus_gcs/theme.py` tokens.
- Use data, not theories (a wrong voltage theory cost trust once). Show check output before saying "fixed". For flight-safety work use `superpowers:systematic-debugging` and `superpowers:verification-before-completion`.
- Skip only cloud parts of Nimbus. Not a git repo (no worktrees).
- Shell traps: a plain `pkill -f "pattern"` inside your own command line kills your own shell (exit 144): kill by PID or from a script file. Keep temp files out of shared `/tmp` if you run several jobs.

## 2. The project
**DroneForge** = replica of NimbusOS adapted to the owner's custom 3-inch drone: ~0.3825 kg, 4S, Matek H743 flight controller running a custom **Betaflight 4.5.4 + on-FC EKF** fork, MTF-02P range+optical-flow sensor on UART3 (`serial 2 262144`), ELRS radio (TX dongle `/dev/serial/by-id/usb-Silicon_Labs_CP2102*`), **DJI O4 Pro** camera via CosmoStreamer RTSP `rtsp://192.168.50.1:554/video`. Goal: **camera-only autonomous indoor roaming** with Nimbus-style perception and control, proven in a Gazebo simulation first, then ported to the real drone. The PC (now this laptop) is the brain; the FC stays in ANGLE mode.

Pipeline (Nimbus style): perception (Depth Anything 3 metric depth -> 6x8 grid + voxel floor plan) -> Kalman filters (12-state lateral + vertical, NIS gate; SuperPoint+LightGlue RGB-D visual odometry as a keyframe position fix) -> LQR tilt control through the Nimbus angle curve `deg = 60(70|s| + 600 s^2)/670` -> jerk-limited speed profile (0.35 m/s^2, 0.8 m/s^3) -> frontier exploration on an occupancy grid with A*. RTAB-Map builds the 2D map.

```
                                                          # If it says CPUExecutionProvider (~3 s/frame) the GPU libraries are not found: fix before anything else.

cd software/pc && python3 -m nimbus_gcs --port /dev/serial/by-id/usb-Silicon_Labs_CP2102*-port0 --connect      # or without args to just look

# Sim, old direct mode (the explorer flies the sim FC directly):
source /opt/ros/jazzy/setup.bash && cd gazebo && ./run_house.sh --gui          # local depth model; add --server URL only to use another machine
```

- Then open the GCS Video page: the right pane shows the RTAB-Map map by itself (stream on 127.0.0.1:5765). Start map also starts the depth client.

## 6. Hard-won facts
- Betaflight Configurator's Ports tab rewrites UART3 and kills range/flow: check `serial 2 262144` (see `configurator-resets-uart3.md`).
- FC voltage reads ~10-20% low and depends on how it is powered; hover throttle comes from flight data, not voltage (`vbat-scale-and-ref.md`).
- ELRS: LQ 0 with a live dongle -> charge pack, start GCS first, power-cycle the battery (`elrs-link-recovery.md`). Never enter the FC CLI within 60 s of power-up.
- Floor lift-off is decided by the ground I-term hold and motor balance (`log24-tipover-and-m4-imbalance.md`, `ground-integrator-windup.md`).
- Wifi to a remote depth server gave ~1 s round trips; that is why everything now runs on one machine. On a GPU the depth model should take ~30 ms.
- Old stale ROS nodes from earlier runs flood the depth server: `run_house.sh` KILL() cleans its own nodes by script name; check `ps` if depth traffic looks wrong.
- `df.py`: `python3 tools_scripts/df.py test [-k name]`, `logs` (FC log download, FC on USB, disarmed, powered >= 60 s), `flash <fw.bin>` (DFU; only with go-ahead).
